# Updating an installed dashboard

Version 0.5.1 is the stable maintenance release, retaining the configuration-preserving updater, dark display and clearer Local RF/Remote presentation. Its new PHP2Shell prerequisite applies to first installations; updating an existing dashboard does not patch or certify PHP. See [release notes](releases/v0.5.1.md).

## Get the current tools

Run as root on the gateway. Download a fresh checkout into a new directory if an older checkout has local edits or line-ending problems:

```bash
git clone https://github.com/KA8SCP/g2_link-legacy-tools.git /root/g2-dashboard-update
bash /root/g2-dashboard-update/scripts/update-dashboard.sh
```

If that checkout already exists and is clean, update it first; only run the updater if the pull succeeds:

```bash
cd /root/g2-dashboard-update
git pull --ff-only && bash scripts/update-dashboard.sh
```

Do not reset or discard local edits to force a pull. A fresh checkout leaves old checkouts and their stashes intact.

## What is preserved

The default destination is `/var/www/html/dashboard`. The updater requires an existing `index.php` and `dashboard.local.php`. It reads the saved callsign, timezone, document root and all four status/log paths without executing the installed PHP as root. It preserves the complete configuration file, including comments, byte for byte, and retains the owner/group of the installed index.php. This preserves existing apache:apache, nginx:nginx and apache:nginx installations.

The current supported configuration is a literal PHP return array with all seven settings, as generated by the installer. Unknown, duplicate, computed or executable settings are rejected rather than replaced with defaults. A site without this baseline must use `install-dashboard-interactive.sh` first. Updates still require a nonempty readable g2_link status feed and a working web PHP setup.

Review the printed callsign, destination, version, source revision, ownership, verification URL and backup path, then answer the single installation confirmation. Cancellation leaves the deployment unchanged. If the configuration changes during review the update stops.

Each run saves a private transcript under `/var/log/g2-dashboard-install/`. Before replacing files it creates a rollback archive and install record under `/var/backups/g2-dashboard/`. Package hashes, PHP syntax and local HTTP/page-content checks are required. Failed deployment/HTTP verification restores the previous dashboard and retains failure files. Extra local files are retained, but package-owned runtime files are replaced. Gateway services, link commands, g2_link.cfg, logrotate, certificates and web server configuration are not modified or restarted.

## Source selection and custom paths

By default the updater requests the latest published stable GitHub Release, rejects draft/prerelease/malformed metadata, and clones its exact tag. Release discovery failure stops the update; it never silently falls back to development code. The fetched source commit is recorded in the footer and install record. Use --ref v0.5.1 to pin this release, or --ref main to explicitly select development code.

```bash
bash scripts/update-dashboard.sh --directory /var/www/html/dashboard --ref v0.5.1
```

For a custom local virtual host or backup location:

```bash
bash scripts/update-dashboard.sh --check-url http://localhost/dashboard/ \
  --backup-root /var/backups/g2-dashboard
```

Only loopback HTTP/HTTPS verification URLs are accepted. HTTPS verification remains enabled; the updater cannot fix missing certificate chains or lost nginx PHP routes. Stop and address those separately if verification fails.

An already reviewed checkout can be installed without another clone:

```bash
bash scripts/update-dashboard.sh --package-dir "$PWD"
```

For a Git checkout the source commit is recorded; a non-Git local package shows the package version without an invented source revision. The updater itself is not silently replaced or re-executed from a downloaded package: refresh the tools checkout before future upgrades.

## Light and dark display

The `Dark display` toggle appears in the page header. Off is the existing light appearance; on uses a dark background, readable table/card surfaces, links and status colors. Keyboard users can activate it as a normal toggle button. The choice is stored in the visitor's browser for that origin, persists across the 60-second refresh and activity-filter navigation, and does not alter gateway settings. Without JavaScript the page remains light; when browser storage is blocked switching still works for the current page, but persistence is unavailable. CSS and JavaScript asset URLs include the dashboard version to refresh cached assets on upgrade.

## Qualification

Automated tests cover saved setting parsing, cancellation, backup/rollback, preserving configuration and ownership, package deployment, invalid inputs and theme persistence/error handling. The updater's HTTP boundary is substituted in the isolated shell test; candidate upgrades were operator-confirmed on WB1GOF (CentOS/Apache) and W4CRL (AlmaLinux/nginx). These reports do not imply every fault case was exercised on each live site. No production gateway was changed during development. See TESTING.md and RELEASE-READINESS.md for the broader qualification matrix.
